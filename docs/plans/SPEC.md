# PulseRelay Webhook-Native Durable Event Relay — Implementation Specification

- **Status:** Proposed
- **Audience:** Oracle Codex / implementation agents / maintainers
- **Repository:** `drtx32/PulseRelay`
- **Primary goal:** Reframe PulseRelay as a durable event gateway with pluggable inputs and webhook-only outbound delivery.

---

## 1. Executive summary

PulseRelay should stop trying to maintain multiple outbound protocols such as long-lived WebSocket sessions, stdio runtimes, MCP transports, or destination-specific agent connections.

The new core model is:

```text
Input Connector
    -> Normalize Event
    -> Persist Event
    -> Match Routes
    -> Aggregate / Trigger
    -> Create Delivery Jobs
    -> Outbound Webhook
    -> Retry / ACK / Audit
```

PulseRelay may still accept events from multiple kinds of inputs:

- inbound webhook
- polling script
- stdio adapter
- WebSocket adapter
- local file/process watcher
- GitHub webhook
- GBrain poller

However, these are **input connectors only**. Every downstream action is represented as an outbound HTTP webhook.

PulseRelay is responsible for:

- receiving events
- normalizing events
- durable persistence
- deduplication
- aggregation
- routing
- reliable webhook delivery
- retries
- replay
- audit logs
- dead-letter handling

PulseRelay is not responsible for:

- running AI agents internally
- writing GitHub directly
- maintaining agent stdio sessions
- maintaining outbound WebSocket sessions
- implementing downstream business workflows
- deciding how Multica, a local agent, or a publisher performs its work

The intended product statement is:

> PulseRelay is a durable event gateway with pluggable inputs and webhook-only delivery.

## 2. Design principles

### 2.1 Persist before side effects

Every inbound event must be committed to durable storage before any outbound webhook is attempted.

Forbidden flow:

```text
receive -> call webhook -> persist
```

Required flow:

```text
receive -> persist event -> persist delivery job -> call webhook -> persist result
```

This prevents an event from disappearing if PulseRelay crashes after the destination has processed it.

### 2.2 At-least-once delivery

PulseRelay must provide **at-least-once** delivery, not pretend to provide exactly-once delivery.

Exactly-once behavior is achieved operationally through:

```text
at-least-once delivery
+
stable idempotency key
+
idempotent downstream consumer
```

A destination may receive the same logical delivery more than once. It must be able to detect duplicates using the supplied idempotency key.

### 2.3 Inputs are adapters; outputs are webhooks

Input protocols may vary. Outbound delivery must use one implementation family:

```text
WebhookDelivery
```

A local agent is therefore exposed as an HTTP endpoint, for example:

```text
POST http://127.0.0.1:9000/jobs
```

Multica is another HTTP destination. A GitHub publisher is another HTTP destination. PulseRelay does not need special delivery classes for each business system.

### 2.4 Route-scoped aggregation

Aggregation thresholds must belong to a route or trigger policy, not to one global TriggerEngine configuration.

Examples:

- GBrain completed output: trigger immediately with one event.
- WeChat investment group: aggregate up to 20 messages, 12,000 characters, 30 seconds idle, or five minutes total age.
- Monitoring alerts: trigger immediately at critical severity, otherwise batch.

### 2.5 Independent fan-out state

For one event or batch sent to multiple destinations, each destination must have an independent delivery row and retry lifecycle.

One failed destination must not invalidate successful delivery to other destinations.

### 2.6 Event chains instead of hidden workflow logic

When actions have dependencies, do not broadcast them simultaneously.

Example:

```text
gbrain.output.ready
    -> wiki-publisher webhook
    -> artifact.published event
    -> multica webhook
```

The second step is triggered by a new durable event emitted after the publisher succeeds. PulseRelay must not hardcode “GitHub then Multica” inside a generic delivery handler.

## 3. Terminology

### 3.1 Source connector

A component that obtains data from an external source and submits a normalized event into PulseRelay.

Examples:

- `WebhookSource`
- `PollingSource`
- `StdioSource`
- `WebSocketSource`
- `FileWatcherSource`
- `GBrainSource`

A source connector must not perform downstream delivery.

### 3.2 Inbound webhook

A public or private URL generated by PulseRelay for external systems to submit events.

Example:

```text
POST /v1/hooks/{endpoint_id}/{secret}
```

### 3.3 Event

An immutable normalized occurrence represented by `EventEnvelope`.

### 3.4 Route

A rule that selects events, defines grouping, defines trigger policy, and points to one or more destinations.

### 3.5 Batch

A durable aggregation of one or more events for a route and group key.

### 3.6 Destination

A configured outbound webhook endpoint.

### 3.7 Delivery

A durable attempt lifecycle for sending one event or batch to one destination.

### 3.8 Checkpoint

A durable cursor used by polling connectors to avoid missing or repeatedly scanning source data.

## 4. Target architecture

```text
External Sources
  WeChat / Slack / Telegram / GBrain / GitHub / Files / Cron / APIs
        |
        v
Input Connectors
  webhook | polling | stdio | websocket | file watcher
        |
        v
Inbound API / Event Normalizer
        |
        v
Durable Event Store
        |
        v
Route Matcher
        |
        v
Route-Scoped Aggregator
        |
        v
Trigger Policy
        |
        v
Delivery Job Store
        |
        v
Webhook Workers
        |
        +------> Local Agent HTTP endpoint
        +------> Multica webhook
        +------> Wiki Publisher HTTP endpoint
        +------> Bark / Slack / Feishu webhook proxy
```

Current PulseRelay components should be evolved, not discarded:

- `EventEnvelope` remains the core normalized representation.
- `EventBus` evolves from in-memory queue compatibility into a durable event inbox abstraction.
- `TriggerEngine` is split into route-scoped aggregation and trigger policy.
- `SQLitePhase9Store` expands to persist routes, batches, deliveries, checkpoints, and endpoint configuration.
- `DeliveryHandler` converges on `WebhookDelivery`.
- `Router` remains responsible for matching and structured decisions, but must not execute business workflows.

## 5. Functional requirements

## 5.1 Inbound webhook endpoints

PulseRelay must support generated inbound URLs.

Suggested endpoint:

```http
POST /v1/hooks/{endpoint_id}/{secret}
Content-Type: application/json
```

An inbound endpoint configuration should include:

```yaml
id: gbrain-production
name: GBrain Production
secret_hash: ...
enabled: true
source_type: gbrain
response_template: '{"accepted": true, "event_id": "{{ event.id }}"}'
normalization_template: optional
max_body_bytes: 1048576
allowed_content_types:
  - application/json
```

Requirements:

1. Validate endpoint and secret.
2. Enforce request-size limit.
3. Parse and normalize payload.
4. Persist the event.
5. Return success only after persistence commits.
6. Do not wait for downstream webhook delivery.
7. Return a stable `event_id`.
8. Support optional HMAC signature verification for third-party webhook sources.

Suggested response:

```json
{
  "accepted": true,
  "event_id": "evt_01...",
  "duplicate": false
}
```

Duplicate submission should normally return `2xx` with `duplicate: true`, not an error.

## 5.2 Polling connectors

PulseRelay must support polling connectors in two modes:

```text
long-running loop
poll-once command
```

Recommended commands:

```bash
pulserelay source run gbrain
pulserelay source poll-once gbrain
```

`poll-once` enables deployment through cron, systemd timer, Kubernetes CronJob, or another scheduler without maintaining a permanent Python loop.

Polling rules:

1. Read the previous checkpoint.
2. Query source records strictly after the checkpoint.
3. Use a deterministic tie-breaker when timestamps match.
4. Normalize each new record.
5. Persist each event idempotently.
6. Advance the checkpoint only after all events in the page/window are durably stored.
7. Never treat “nothing found” as having consumed an expected business schedule slot.

Recommended checkpoint shape:

```json
{
  "updated_at": "2026-08-18T13:53:13.850Z",
  "tie_breaker": "tasks/runs/trendradar-digest/2026-08-18-200000"
}
```

## 5.3 GBrain source connector

The first high-value polling connector should be the mounted
`connectors/gbrain/` connector. Its polling and normalization logic may be
implemented as `GBrainSource` internally, but it must run as an independent
connector process and submit normalized events to PulseRelay.

It must discover task runs satisfying:

```yaml
status: completed
verification: passed
output_slug: present
```

It must then read `output_slug` and generate an event only after confirming the output page exists.

Do not scan based on the scheduled time alone. A task starting at 08:00 and finishing at 08:20 must still be discovered by a poll at 08:21 even if a poll at 08:10 found nothing.

Suggested event:

```json
{
  "id": "gbrain:trendradar-digest:2026-08-18-200000",
  "source": {
    "type": "gbrain",
    "id": "tasks/runs/trendradar-digest/2026-08-18-200000",
    "name": "GBrain"
  },
  "sender": {
    "id": "chatgpt",
    "name": "ChatGPT Task Runner",
    "role": "agent",
    "trust_level": "trusted"
  },
  "event": {
    "type": "gbrain.output.ready",
    "action": "publish",
    "timestamp": "2026-08-18T13:53:00Z",
    "dedupe_key": "tasks/runs/trendradar-digest/2026-08-18-200000:CONTENT_HASH"
  },
  "content": {
    "title": "TrendRadar digest ready",
    "text": "",
    "raw": {
      "source_run": "tasks/runs/trendradar-digest/2026-08-18-200000",
      "output_slug": "notes/trendradar-digests/2026-08-18-2000",
      "content_hash": "..."
    }
  },
  "context": {
    "project_id": "investment-research"
  },
  "routing": {
    "priority": "normal",
    "labels": ["gbrain", "publish", "trendradar"]
  }
}
```

Recommended deduplication modes:

```yaml
# Publish each task run only once.
dedupe_mode: source_run

# Republish a corrected output when content changes.
dedupe_mode: source_run_and_content_hash
```

The default should be `source_run_and_content_hash` because it supports corrected reports without losing idempotency.

## 5.4 Stdio and WebSocket inputs

Stdio and WebSocket support may remain, but only as external input adapters.

Example stdio adapter:

```text
read stdin
-> create EventEnvelope
-> POST PulseRelay inbound API
-> exit or continue reading
```

Example WebSocket adapter:

```text
connect remote WebSocket
-> receive message
-> create EventEnvelope
-> POST PulseRelay inbound API
```

Core PulseRelay must not expose destination-specific stdio or outbound WebSocket delivery semantics.

## 5.5 Route matching

A route must support matching on at least:

- source type
- source id
- event type
- event action
- sender id / role / trust level
- labels
- project id
- conversation id
- arbitrary JSON-path-compatible metadata fields

Example:

```yaml
id: gbrain-publish
match:
  source.type: gbrain
  event.type: gbrain.output.ready
group_by:
  - content.raw.source_run
trigger:
  mode: immediate
destinations:
  - wiki-publisher
```

Routes may overlap. One event can enter several routes.

## 5.6 Many-to-many topology

The data model must naturally support:

### One-to-many

One event/batch delivered to several destinations.

```text
gbrain.output.ready
  -> wiki-publisher
  -> audit-webhook
  -> bark-notification
```

### Many-to-one

Many source events aggregated into one batch.

```text
WeChat + Slack + Telegram
  -> topic batch
  -> research-agent
```

### Many-to-many

Several sources can feed several routes, and each route can target several destinations.

Do not implement one-to-many, many-to-one, and many-to-many as separate workflow types. They must emerge from relational mappings:

```text
route_sources
route_destinations
batch_events
```

## 5.7 Aggregation policy

Each route may define:

```yaml
aggregate:
  enabled: true
  group_by:
    - context.conversation_id
  max_events: 20
  max_chars: 12000
  idle_timeout_seconds: 30
  max_wait_seconds: 300
```

A batch becomes ready when any condition is satisfied:

```text
event_count >= max_events
OR total_chars >= max_chars
OR idle_time >= idle_timeout
OR now >= first_event_at + max_wait
```

`max_wait` is mandatory when aggregation is enabled. Without it, a continuously active stream might never flush.

Immediate route example:

```yaml
aggregate:
  enabled: false
trigger:
  mode: immediate
```

For an immediate route, one event produces one ready batch or direct delivery unit.

## 5.8 Event chaining

A destination may optionally return a normalized result event.

Example publisher result:

```json
{
  "status": "success",
  "emit": {
    "event_type": "artifact.published",
    "dedupe_key": "gbrain:trendradar:2026-08-18-200000:github",
    "content": {
      "text": "Published to LLM-Wiki",
      "raw": {
        "source_event_id": "gbrain:trendradar-digest:2026-08-18-200000",
        "repository": "drtx32/LLM-Wiki",
        "path": "reports/trendradar-digests/2026/08/2026-08-18-2000.md",
        "commit_sha": "..."
      }
    }
  }
}
```

PulseRelay must validate and persist the emitted event before routing it.

This allows:

```text
gbrain.output.ready
-> wiki-publisher
-> artifact.published
-> Multica webhook
```

Do not encode this dependency inside the delivery implementation.

## 6. Outbound webhook delivery

## 6.1 Destination configuration

```yaml
id: multica-research
name: Multica Research Automation
url: https://example.com/hooks/...
method: POST
enabled: true
timeout_seconds: 30
max_attempts: 10
retry_policy:
  type: exponential
  initial_seconds: 10
  max_seconds: 3600
headers:
  Authorization: "Bearer ${MULTICA_TOKEN}"
  Content-Type: application/json
payload_template: |
  {
    "event_id": "{{ event.id }}",
    "delivery_id": "{{ delivery.id }}",
    "title": {{ batch.title | tojson }},
    "content": {{ batch.text | tojson }},
    "metadata": {{ batch.metadata | tojson }}
  }
success_statuses:
  - 200
  - 201
  - 202
  - 204
```

Secrets must be referenced from environment/secret storage, never persisted in plaintext configuration exported through APIs or logs.

## 6.2 Standard request headers

PulseRelay must send:

```http
X-PulseRelay-Event-ID: <event or batch id>
X-PulseRelay-Delivery-ID: <delivery id>
X-PulseRelay-Timestamp: <unix or ISO timestamp>
X-PulseRelay-Signature: <HMAC signature>
Idempotency-Key: <stable key>
```

Suggested idempotency key:

```text
{event_or_batch_id}:{destination_id}:{payload_version}
```

The key must remain stable across retries of the same logical delivery.

## 6.3 Delivery result

```python
DeliveryResult(
    status="success" | "failed" | "skipped",
    external_id="optional downstream job or commit id",
    http_status=200,
    response_excerpt="bounded, redacted text",
    error="",
)
```

The response body must be size-limited before persistence. Secrets and sensitive headers must never be stored.

## 6.4 Retry behavior

Recommended schedule:

```text
10s -> 30s -> 2m -> 10m -> 1h -> 1h ...
```

Requirements:

1. Retry network errors and configured HTTP statuses such as 408, 429, and 5xx.
2. Honor `Retry-After` when valid.
3. Do not retry permanent 4xx failures unless explicitly configured.
4. Increment delivery attempts per outbound attempt.
5. Move exhausted deliveries to dead letter.
6. Preserve the original event and batch.
7. Provide manual replay.

## 6.5 Claim/lease semantics

Workers must claim deliveries using a lease to prevent simultaneous duplicate sending by several workers.

Suggested fields:

```text
claimed_by
claimed_at
lease_expires_at
```

A worker may claim only:

```text
status in (pending, retrying)
AND next_attempt_at <= now
AND lease is absent or expired
```

After crash or lease timeout, another worker may retry.

## 7. Data model

SQLite remains acceptable for the initial implementation. Schema should remain portable to PostgreSQL.

## 7.1 `events`

```sql
CREATE TABLE events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    event_id TEXT NOT NULL UNIQUE,
    source_type TEXT NOT NULL,
    source_id TEXT NOT NULL DEFAULT '',
    event_type TEXT NOT NULL,
    event_action TEXT NOT NULL DEFAULT '',
    dedupe_key TEXT NOT NULL UNIQUE,
    payload_json TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'received',
    received_at TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

An event is logically immutable. Status and operational metadata may change; the original normalized payload must not be silently rewritten.

## 7.2 `routes`

```sql
CREATE TABLE routes (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    enabled INTEGER NOT NULL DEFAULT 1,
    match_json TEXT NOT NULL,
    aggregation_json TEXT NOT NULL,
    trigger_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

## 7.3 `route_destinations`

```sql
CREATE TABLE route_destinations (
    route_id TEXT NOT NULL,
    destination_id TEXT NOT NULL,
    ordinal INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (route_id, destination_id)
);
```

## 7.4 `batches`

```sql
CREATE TABLE batches (
    id TEXT PRIMARY KEY,
    route_id TEXT NOT NULL,
    group_key TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'collecting',
    event_count INTEGER NOT NULL DEFAULT 0,
    total_chars INTEGER NOT NULL DEFAULT 0,
    first_event_at TEXT NOT NULL,
    last_event_at TEXT NOT NULL,
    idle_deadline_at TEXT,
    max_wait_deadline_at TEXT NOT NULL,
    ready_at TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

## 7.5 `batch_events`

```sql
CREATE TABLE batch_events (
    batch_id TEXT NOT NULL,
    event_id TEXT NOT NULL,
    ordinal INTEGER NOT NULL,
    PRIMARY KEY (batch_id, event_id)
);
```

## 7.6 `destinations`

```sql
CREATE TABLE destinations (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    enabled INTEGER NOT NULL DEFAULT 1,
    url TEXT NOT NULL,
    method TEXT NOT NULL DEFAULT 'POST',
    config_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

Secret values must not be stored directly in `config_json`; store references such as environment variable names.

## 7.7 `deliveries`

```sql
CREATE TABLE deliveries (
    id TEXT PRIMARY KEY,
    event_id TEXT,
    batch_id TEXT,
    destination_id TEXT NOT NULL,
    idempotency_key TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'pending',
    attempts INTEGER NOT NULL DEFAULT 0,
    next_attempt_at TEXT,
    claimed_by TEXT,
    claimed_at TEXT,
    lease_expires_at TEXT,
    http_status INTEGER,
    external_id TEXT,
    response_excerpt TEXT NOT NULL DEFAULT '',
    last_error TEXT NOT NULL DEFAULT '',
    completed_at TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE (idempotency_key)
);
```

Exactly one of `event_id` or `batch_id` should be populated.

## 7.8 `connector_checkpoints`

```sql
CREATE TABLE connector_checkpoints (
    connector_id TEXT PRIMARY KEY,
    cursor_json TEXT NOT NULL,
    last_success_at TEXT,
    last_error TEXT NOT NULL DEFAULT '',
    updated_at TEXT NOT NULL
);
```

## 7.9 Existing audit and dead-letter tables

Retain and expand existing `audit_logs` and `dead_letters` rather than introducing parallel implementations.

## 9. Templates and transformations

Support limited templates for:

- inbound normalization
- inbound HTTP response
- batch title/text formatting
- outbound payload
- outbound headers

Use a sandboxed template implementation. Do not expose Python `eval`, arbitrary imports, filesystem access, process access, or network access through templates.

Template errors must:

1. fail the affected delivery or inbound normalization clearly;
2. be recorded in audit/dead-letter storage;
3. never crash the entire worker process.

---

## 10. Security requirements

1. Store webhook secrets as hashes where comparison is sufficient.
2. Store destination credentials through secret references, not plaintext.
3. Support outbound HMAC signing.
4. Support inbound HMAC verification.
5. Enforce timestamp windows to reduce replay attacks.
6. Enforce body-size limits.
7. Restrict redirects for outbound requests; do not allow credential leakage across hosts.
8. Block loopback/private-network destinations by default in hosted mode; allow them explicitly in trusted local mode.
9. Apply SSRF protections to user-configurable outbound URLs.
10. Redact authorization headers, cookies, tokens, query secrets, and signed URLs from logs.
11. Provide per-endpoint rate limits.
12. Preserve raw payload only when configured; otherwise retain a bounded/redacted version.
13. Never execute instructions embedded in inbound event content.

## 12. Failure semantics

### 12.1 Inbound persistence failure

Return non-2xx. The sender may retry with the same dedupe key.

### 12.2 Duplicate inbound event

Return 2xx with the existing event ID and `duplicate: true`.

### 12.3 Route/template failure

Record audit and dead letter. Preserve the event.

### 12.4 Destination unavailable

Schedule retry. Do not mark the event failed globally.

### 12.5 One destination succeeds and another fails

Keep independent states. Do not resend the successful destination when retrying the failed destination.

### 12.6 Worker crash after downstream success but before ACK persistence

The delivery may be sent again after lease expiry. The downstream idempotency key must prevent duplicate business execution.

## 13. Migration from current PulseRelay

Do not rewrite the project from zero.

### Keep

- `core/event.py` / `EventEnvelope`
- compatibility wrappers for existing message-shaped inputs
- current `EventBus` API where practical
- existing SQLite storage, audit, replay, and dead-letter concepts
- current router concepts
- source modules
- existing tests where behavior remains valid

### Refactor

- Split `TriggerEngine` into:
  - `Aggregator`
  - `TriggerPolicy`
- Move trigger config from global engine configuration to route configuration.
- Make `EventBus` persistence-first rather than memory-first when a store is attached.
- Replace destination-specific outbound mechanisms with `WebhookDelivery`.
- Add durable delivery lifecycle and worker leases.
- Add connector checkpoints.
- Convert existing stdio/WebSocket integration to inbound adapters.

### Deprecate

- outbound stdio delivery
- outbound WebSocket delivery as a core contract
- hidden execution of local agents from inside the router
- message-only routing assumptions
- global aggregation thresholds

Compatibility may remain for one release, but new implementation and docs must use event-native terminology.

## 15. Implementation phases

## Phase 1 — Durable delivery foundation

Deliverables:

- schema migration for destinations and deliveries
- `WebhookDelivery`
- delivery claim/lease
- retries and dead-letter
- standard headers and idempotency keys
- delivery API/readback
- unit tests

Acceptance:

- one event can create delivery jobs for two destinations;
- one destination can fail and retry without resending the successful destination;
- process restart does not lose pending deliveries.

## Phase 2 — Route-scoped aggregation

Deliverables:

- route configuration persistence
- event matching
- group key calculation
- durable batches
- max events, max chars, idle timeout, max wait
- immediate mode

Acceptance:

- GBrain route triggers on one event;
- WeChat route batches several events;
- continuous traffic still flushes at `max_wait`.

## Phase 3 — Inbound webhook product surface

Deliverables:

- generated inbound webhook endpoints
- secret validation
- HMAC verification
- response templates
- request limits/rate limits
- endpoint management API

Acceptance:

- a third-party POST is persisted before receiving 2xx;
- duplicate POST returns existing event ID;
- invalid signatures are rejected.

## Phase 4 — GBrain polling connector

Deliverables:

- GBrain run discovery
- output-page verification
- durable checkpoint
- `source_run_and_content_hash` dedupe mode
- `poll-once` and long-running modes

Acceptance scenario:

```text
08:00 run starts
08:10 poll finds no completed output
08:20 run completes
08:21 poll emits exactly one event
```

No scheduled slot may be permanently skipped merely because an earlier poll found nothing.

## Phase 5 — Event chaining

Deliverables:

- validated emitted result events from webhook responses
- persistence before routing
- parent/causation metadata

Acceptance:

```text
gbrain.output.ready
-> publisher succeeds
-> artifact.published persisted
-> Multica delivery created
```

Multica must not trigger if publisher delivery has not succeeded.

## Phase 6 — Connector simplification

Deliverables:

- stdio inbound adapter
- WebSocket inbound adapter
- documentation that outbound transport is webhook-only
- compatibility/deprecation notices

## 17. Acceptance criteria

The implementation is complete when all statements below are true.

1. PulseRelay can receive an event through a generated inbound webhook URL.
2. PulseRelay can receive equivalent events from polling, stdio, and WebSocket input adapters.
3. All events are durably stored before downstream actions.
4. One event can fan out to several webhook destinations with independent states.
5. Several events can be aggregated into one route-specific batch.
6. Several sources and several destinations can be connected through route tables without special workflow classes.
7. Immediate routes trigger from one event.
8. Aggregated routes support max count, max characters, idle timeout, and mandatory max wait.
9. Outbound delivery is webhook-only at the core contract level.
10. Failed deliveries retry after restart.
11. Downstream idempotency keys remain stable across retries.
12. Dead-letter and replay are available.
13. A GBrain result that finishes after an earlier empty poll is still discovered and delivered.
14. Dependent workflows are implemented as chained events, not simultaneous fan-out.
15. Secrets do not appear in logs, event payloads, API output, or audit records.
16. Existing WeChat/message-centric behavior remains functional through compatibility adapters during migration.
17. The full test suite passes.

## 18. Oracle Codex execution guidance

Oracle Codex should:

1. Inspect existing code and tests before modifying architecture.
2. Preserve compatibility where practical rather than deleting existing behavior immediately.
3. Implement schema migration safely and idempotently.
4. Prefer small, test-backed phases over one massive rewrite.
5. Keep the core transport contract HTTP-based.
6. Keep business-specific publishing logic outside PulseRelay.
7. Do not hardcode GBrain, GitHub, Multica, WeChat, or a particular agent into the core router.
8. Treat inbound event content as data, never executable instructions.
9. Add or update documentation as each phase lands.
10. Stop and report any design conflict where an existing public API cannot be preserved without unsafe ambiguity.

The first implementation target should be:

```text
Phase 1 -> Phase 2 -> Phase 4
```

This sequence delivers the immediate GBrain use case while establishing the reusable delivery and aggregation foundations.

## 20. Non-goals for the first release

- distributed consensus
- Kafka compatibility
- exactly-once delivery claims
- arbitrary user code in templates
- a full visual workflow editor
- internal LLM execution
- internal GitHub publishing implementation
- hosted multi-tenant billing
- cross-region active-active delivery

These may be considered later, but they must not delay the durable webhook-native foundation.
